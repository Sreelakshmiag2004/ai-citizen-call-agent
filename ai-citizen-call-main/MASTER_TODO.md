  - **Status:** Fixed and verified 2026-08-19. `_validate_audio_file()` was previously duplicated verbatim in `transcription.py`, `analysis.py`, and `complaints.py`; replaced with one shared `validate_and_read_audio_file()` in a new `app/services/audio_validation.py`, called identically from all three (`/transcribe`, `/process-complaint`, `/process-and-create-ticket`). Allowed extensions unchanged (`.wav`, `.mp3`, `.m4a`, `.webm`, `.mp4`).
  - **What's already completed:** A configurable max upload size (`MAX_AUDIO_UPLOAD_MB` env var, default 25 MB) is enforced while streaming in 1 MB chunks with a running byte count -- an oversized upload is rejected with **413** as soon as the running total crosses the limit, without ever buffering the full file into memory first. Content is validated against real file-signature/magic-byte checks per format (RIFF/WAVE for `.wav`, ISO-BMFF `ftyp` box for `.m4a`/`.mp4`, EBML magic for `.webm`, ID3/frame-sync for `.mp3`, with a lenient-but-effective bar for the latter since MP3 has no single universal signature) -- an explicit deny-list also catches obvious mismatches (a PNG/JPEG/PDF/ZIP/executable renamed to an audio extension) regardless of which extension it was renamed to. The client-supplied `Content-Type` header is never consulted anywhere in this logic (verified live: a real WAV sent with a wrong Content-Type still succeeds; fake content sent with a correct-looking `audio/wav` Content-Type is still rejected). Empty-file rejection (400) is preserved.

Built and verified across 5 stages (below); Twilio, the complaint duplicate-detection pipeline, and existing Groq transcription/analysis behavior were never touched by any of it.
